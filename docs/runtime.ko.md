# 런타임

`Pool::new`은 `entry_path`, `entry_bytes`와 정확한 비공개 서버 경로·바이트의 `chunks`를 담은
`ServerBundle`과 명시적인 `PoolOptions`를 받는다. 풀은 V8 스냅샷에서 진입점을 모듈로 평가하고, 워커마다
하나의 스레드에서 스냅샷으로 만든 isolate를 소유한다. 진입점은 `render(props, state)`를
export하며 함수는 context 데이터에 보관되고 전역 객체에는 없다. 제공된 모든 서버 파일은 풀 생성 시
컴파일하고 정적 import를 해석하며, 동적 청크는 import할 때 평가한다. 정적·동적 상대 import는 제공된
서버 파일만 대상으로 해석한다. 누락·중복 파일, 잘못된 경로, import 속성, 평가 실패와 끝나지 않은
최상위 await는 오류다. JavaScript 구문 오류는 V8 `SyntaxError` 진단을 JavaScript 오류로 반환한다.
서버 파일 경로는 `server/`로 시작하고 `.js`로 끝나며 빈 요소, 점 요소,
역슬래시, 콜론, 제어 문자가 없어야 한다. import 지정자는 query와 fragment가 없는 상대 경로다.
유효한 정적 import 순환은 V8 모듈 평가를 따른다. 각 파일은 매니페스트
경로를 JavaScript 소스 이름으로 사용하므로 해당 소스맵이 스택 위치를 해석한다. 렌더 함수는 필수 문자열
`html`, `head`와 JSON `state` 값이 있는 객체를 직접 또는 Promise로 반환한다. head 누락이나
잘못된 값은 오류이며 UTF-8 바이트가 `RenderResult`에 남는다. 런타임은
Promise의 결과를 읽기 전에 대기 중인 V8 microtask를 완료한다. Promise가 거부되면
메시지와 stack을 가진 JavaScript 오류를 반환한다. microtask 완료 후에도 대기하는
Promise는 이를 완료할 외부 이벤트 원천이 없으므로 오류다. 함수 부재, 잘못된 결과,
JavaScript 예외도 오류다. 호출자는 SSR `Page`를 전달하고 `RenderResult`를 받는다.
라이브러리 워크스페이스는 S-4-2에서 검증한 같은 V8 150.4.0 소스 체크아웃을 선택하고,
관리 중인 식별자 매크로 의존성을 `Cargo.lock`에 고정한다.

스냅샷 키에는 정렬된 서버 파일 경로·바이트 SHA-256, 고정된 deno_core 버전과 라이브러리 버전이
들어간다. 프로세스는 초기화 성공 시 키 하나를 선택하고 스냅샷을 종료까지 유지한다. 같은 키는 같은
바이트를 재사용하며 모든 풀이 종료된 뒤에도 다른 키는 명시적인 오류를 반환한다. 운영 빌드 명령과 렌더
서버는 별도 Rust 프로세스를 사용하고 새 앱 버전은 새 렌더 프로세스에서 시작한다.

`polyspec_ssr_core::process::build`는 Svelte 컴파일러의 V8 생성부터 런타임 정리까지 보호한다.
`polyspec_ssr_core::process::render`는 스냅샷 생성부터 생성기 정리까지 보호한다. 컴파일러끼리 동시 실행은
허용하며 스냅샷 작업은 동시 엔진 진입을 거부한다. 스냅샷이 성공한 뒤에는 V8 생성 전에 컴파일러
진입이 실패한다. 일반 Rust 번들링은 계속 사용할 수 있다. 완료한 Svelte 빌드 뒤에 같은 프로세스에서
렌더할 수 있다. 스냅샷 초기화 실패는 마지막 isolate를 정리한 뒤 접근을 해제하므로 후속 컴파일과
렌더를 다시 시도할 수 있다. 잠금 경합과 오염된 잠금은 오류를 반환하며 대기하거나 프로세스 계약을 우회하지 않는다.

공개 V8 스냅샷 생성기는 프레임워크와 앱을 한 번 평가하고 context를 직렬화한 뒤 워커 생성 전에
완전히 정리된다. 워커는 공개 isolate API와 검증한 공식 로컬 archive로 같은 스냅샷을 동시에
복원한다. 호출마다 별도 context를 복원하며 어느 번들도 다시 실행하지 않는다. 초기화된 전역과
Web API는 각 context에 제공되고 요청에서 변경한 값은 후속 호출에 영향을 주지 않는다. 초기화
실패는 프로세스 키를 선택하지 않고 해당 오류를 반환하며 설정한 제한 시간을 적용한다.
Props와 입력 상태는 V8 값으로 전달한다. HTML, head와 출력 상태는 바이트로 반환하고 출력 상태는
ordered-json으로 파싱한다.
출력 상태에 undefined, 함수, symbol, bigint 또는 유한하지 않은 숫자가 있으면
조용히 제외하거나 null로 바꾸지 않고 실패한다. 잘못된 입출력은 기본값으로 바꾸지 않고
오류를 반환한다.

`PoolOptions`는 `worker_count`, `queue_capacity`, `timeout`, `cleanup_timeout`,
`max_input_bytes`, `max_queue_bytes`, `max_chunk_bytes`, `max_output_bytes`, `max_heap_bytes`를
정의한다. 대기열 수를 제외한 한도는 양수여야 하며 대기열 수가 0이면 대기 바이트도 0일 수 있다.
`validate`는 스냅샷이나 워커 생성 전에 잘못된 한도를 거부한다. 입력 바이트는 compact props·입력
상태·nonce를 포함한다. 대기 바이트는 워커를 기다리는 직렬화된 요청의 크기다. 출력 바이트는
출력 상태와 모든 HTML 청크를 포함하며 일반 렌더에는 head도 포함한다. 힙 한도는 V8 힙 할당을
설정한다. 전체 네이티브 할당을 제한하거나 치명적인 V8 할당 실패를 격리하지 않으며 프로세스
메모리 한도와 교체는 프로세스 관리자의 책임이다.

모든 워커가 실행 중이면 설정한 수만큼 호출이 대기한다. 추가 호출은 `QueueFull`, 바이트 한도
초과는 출력 일부를 반환하지 않고 `LimitExceeded`를 반환한다. `render_with_metrics`는 풀 대기,
context 생성 시간과 힙 변화, 렌더 후 V8 사용 힙을 반환한다. `render`는 같은 결과를 메트릭 없이
반환한다. `Pool::health`는 현재 가용 상태를 반환한다. `Pool::wait`는 종료 이벤트를 기다린 뒤
폴링 없이 워커 오류를 반환한다. `Pool::close`는 새 호출을 거부하고 요청을 취소하며
`cleanup_timeout` 안에 스레드를 정리한다. 워커를 정리하지 못하면 전체 풀이 사용 불가가 되고
프로세스 교체가 필요하다. 대체 워커 스레드는 만들지 않는다. 초기화와 워커 정리가 모두
실패하면 반환 오류에 두 원인을 보존한다.

복원한 context는 진단을 표준 오류에 기록하는 `console` 메서드와 운영체제 난수를 사용하는
`crypto.getRandomValues`를 제공한다. 난수 메서드는 최대 65,536바이트의 정수
typed-array view를 받고 해당 view만 변경한다. 잘못된 인자, 정수가 아닌 view 및
초과 길이는 오류를 던진다. 두 Web Crypto 오류에 필요한 DOMException 이름과 코드를
제공하며, 관련 없는 DOM API는 없다. 운영체제 오류가 나면 view를 변경하지 않는다.
`fetch`, 파일·네트워크 접근 및 I/O 타이머는 없다. 서버 번들은 신뢰하는 애플리케이션 코드이며
프로세스 격리를 얻지는 않는다.

모든 렌더 context는 UTF-8 `encoding`, `encode`, `encodeInto`를 가진 `TextEncoder`도 제공한다.
인코딩은 단독 서로게이트를 U+FFFD로 바꾼다. `encodeInto`는 UTF-8 시퀀스 일부를 쓰지
않고 읽은 UTF-16 코드 단위와 쓴 바이트의 수를 반환한다. 잘못된 수신자와 대상은
TypeError를 던진다. 이 인터페이스는 React 서버 번들이 필요한 인코딩을 제공하며
파일·네트워크·타이머 연산을 노출하지 않는다.

`Pool::new_react`는 비공개 프레임워크 경로·바이트, 서버 청크가 없는 애플리케이션
`ServerBundle`, `PoolOptions`를 받는다. 프레임워크와 애플리케이션을 같은 스냅샷
context에서 한 번 초기화하므로 애플리케이션 모듈 초기화와 렌더가 같은 React 인스턴스를
사용한다. 프레임워크 번들은 작업 예약과 Web Streams를 어휘 인자로 받는 함수로 실행한다.
애플리케이션 번들 실행 전에 전역 `setTimeout`을 제거하므로 애플리케이션 코드는 I/O 타이머를
예약할 수 없다. `Pool::render_stream` 호출마다 새 `Cancellation`을 받고 별도 요청 context를 복원하며 렌더를 실행해
셸이 준비되면 출력 상태와 스트림을 반환한다. 스트림은 두 번들을 다시 실행하지 않고 HTML
청크를 전달하며 셸 이후의 실패는 명시적 스트림 오류다. fixture는 최상위 React 클래스와
context를 `useId`, `useContext`와 함께 렌더하고 애플리케이션 타이머 경계를 확인한다.

완료 기준: 추적되는 테스트가 스냅샷 재사용과 키 불일치, 초기화 상태 복원, 초기화 실패와 시간 초과,
요청 격리, 종료되지 않는 스크립트, 대기열 포화,
대기와 실행을 합친 기한, 응답하지 않는 워커의 제외와 대기 호출 통지, 표준 오류에서
확인한 console 출력, 난수와 인자 오류, 금지 API 부재를 검증한다. 각 테스트에는
`make check` 실행 시 제한 시간이 적용되며, 표준 오류 확인 하위 프로세스에도 별도의
제한 시간이 적용된다.
Promise 테스트는 이행, stack을 가진 거부, 완료되지 않은 결과를 확인한다. React 번들
사례는 최상위 React 선언을 가진 애플리케이션 컴포넌트를 실행한다.
React 스트림 사례는 반복 요청 context, 서로 다른 렌더 프로세스에서 애플리케이션 스냅샷 복원, 실패한
Suspense 경계의 클라이언트 복구 지시 보존을 확인한다.

## 요청 취소와 한도

설정한 요청 시간은 풀 대기·실행·스트림 전송에 적용한다. 스트림 종료는 청크 전송의 네이티브
대기를 포함해 해당 요청을 취소한다. 취소와 완료는 요청별 상태를 공유하며, 완료된 요청은
다른 요청을 처리하는 isolate를 종료할 수 없다. context 해제와 실행 종료 상태 정리가
끝난 뒤에만 용량을 반환한다. 풀 상태는 워커 실패를 보고하고, 풀 종료는 활성 호출을 취소하며
설정한 정리 시간 안에 스레드를 정리하지 못하면 실패를 보고한다. 중단할 수 없는 네이티브
호출은 프로세스 교체가 필요하며 풀은 대체 스레드를 만들지 않는다. 직렬화한 입력·대기 입력
바이트·청크 바이트·전체 출력 바이트에 명시한 한도를 적용한다. 큰 V8 청크는 복사 전에
분할해 각 전송 청크가 `max_chunk_bytes`를 지키면서 전체 출력과 순서를 보존한다. 입력·대기·
전체 출력 한도 초과는 오류이며 출력 일부를 성공으로 반환하지 않는다.

스트림 요청 전에 `Cancellation::new()`로 만든 값을 복제해
`render_stream(page, nonce, cancellation)`에 전달한다. `cancel()`은 대기와 실행 중인 작업을
중단한다. 토큰은 요청 하나에만 사용하며 재사용은 오류다. `Stream::cancel_handle`은 같은 토큰을
복제한다. 스트림을 제거하면 호출자를 막지 않고 취소를 요청한다. 워커마다 고정된 관측 스레드가
있어 수신자가 `next`를 호출하지 않아도 취소·시간 만료·정리 완료를 확인한다. `Stream::close`는
취소를 요청하고 정리 완료 여부를 보고한다. 요청 실패와 정리 실패가 함께 발생하면 둘 다
오류에 보존한다. 실행 종료 상태를 해제하고 워커를 반환한 뒤 완료를 알린다. 완료된 토큰은
다음 요청을 종료할 수 없다.

런타임 tracing은 실행 시작·취소 확인·정리 완료에서 요청 nonce·워커 번호·경과 시간을 기록한다.
렌더 실패는 종료 이벤트 전송 전에 기록하므로 수신 연결이 끊겨도 실패 진단이 누락되지 않는다.

워커 용량을 예약한 뒤 워커가 명령을 받기 전에 요청 시간이 만료되거나 취소되면 해당 요청만
실패시키고 예약 용량을 반환한다. 워커 명령 수신 연결이 끊기면 풀을 사용 불가로 만들며 해당
워커를 가용 용량에 반환하지 않는다.

초기화 뒤 네이티브 워커나 관측 스레드에서 unwind가 발생하면 스레드 정리가 풀을 사용 불가로
만들고 추가 요청이나 본문 읽기 없이 `Pool::wait`를 깨운다.
